# Стартовые материалы единого индивидуального проекта

Материалы рассчитаны на PostgreSQL 18, PHP 8.4 и Docker Compose v2. Нужны Docker Engine, Bash, curl и openssl. В Windows используйте WSL. В этих каталогах нет завершённого решения предметного задания.

Проверка поставки: синтаксис Bash и конфигурации Compose проверены статически. Docker Engine в среде подготовки недоступен; сборка образа, выполнение PHP/SQL и работа репликации здесь не проверялись. Перед использованием на занятиях необходим контрольный запуск преподавателем.


## Один проект от лабораторных до курсовой

Каждый студент выбирает один из 15 вариантов и сохраняет его на протяжении ЛР 1–4 и КР. Соответствующие задания содержатся в документах «ЛР — единый индивидуальный проект» и «КР — углубление индивидуального проекта». Прежнее деление на профили А/Б/В не используется.

Лабораторный минимум — фрагмент из 4–5 сущностей, три предметные операции API, два запроса и одна защищённая критическая операция. КР расширяет этот проект до двух предметных сценариев, 5–7 операций и исследования по вопросу своего варианта. ЛР 5 использует отдельную локальную конфигурацию ha; её протокол хранится в том же репозитории проекта.

Номера и темы перечислены в VARIANTS.md. Полное индивидуальное задание, включая обязательное углубление и опыт, находится в документе КР. В templates добавлены формы фиксации инвариантов, развития проекта, проверок, исследования и переключения; это пустые формы, а не готовые ответы.

Сохраняйте версии lab1–lab5 и kr-final. Не добавляйте .env, токены, пароли и каталоги БД в сдаваемый архив. Комментарии и документация в коде допустимы. Файлы из examples помогают освоить инструмент, но не заменяют собственную предметную реализацию.

## Индивидуальный проект

1. В starter выполните `bash tools/init-env.sh`.
2. До первого занятия по реализации выполните `docker compose build web` и загрузку образа `docker compose pull db migrate`. Для первой сборки нужны сеть и доступ к пакетам Debian. Это подготовка среды, а не предметное задание.
3. В ЛР 1 создайте `db/migrations/001_schema.sql` со своей схемой app.
4. Выполните `docker compose up -d --build`, затем `docker compose run --rm migrate`.
5. Проверьте `curl -i http://127.0.0.1:8080/health/db` и `bash tests/smoke.sh`.
6. Добавьте три предметных обработчика, фикстуры и восемь проверок из `tests/contract.example.md`.

Из компьютера PostgreSQL доступен по 127.0.0.1:55432. Внутри API адрес — db:5432. .env не коммитить и не включать в отчёты. После первого успешного запуска сохраните точную версию и digest образов (`docker compose images`, `docker image inspect`), не публикуя конфигурацию с раскрытыми секретами.

lab_admin создаётся образом для настройки стенда. lab_owner владеет схемой app и выполняет миграции. web_app имеет права чтения и изменения предметных таблиц, но не создания таблиц и изменения истории миграций. Права на будущие объекты задаются ALTER DEFAULT PRIVILEGES владельца. Служебные маршруты показывают только доступность. Разделение владельцев строк и бизнес-операции нужно реализовать студенту.

В ЛР 4 подключите `lab_user()` из src/auth.php к предметным маршрутам. Она возвращает id и role по трём случайным токенам окружения: LAB_USER_TOKEN (id=1, user), LAB_OTHER_TOKEN (id=2, user), LAB_MANAGER_TOKEN (id=3, manager). Добавьте соответствующих участников в свои фикстуры либо осмысленно адаптируйте сопоставление. Это учебная аутентификация, без регистрации, отзыва и внешнего провайдера. Проверка владельца, роли, SQL-ограничений и транзакций остаётся заданием.

Для отдельных проверок используйте `docker compose exec db psql -U lab_admin -d webdb`. Для проверки роли приложения: `docker compose exec web php -r 'require "/var/www/src/bootstrap.php"; var_dump(db()->query("SELECT current_user")->fetchColumn());'`. Привилегированное подключение не должно появляться в обработчиках API.

Для развёртывания отдельной чистой копии используйте другое имя проекта и другие порты, например `WEB_PORT=18080 DB_PORT=55442 docker compose -p webdb-check up -d --build`, затем `docker compose -p webdb-check run --rm migrate`. Исходный проект остаётся на прежних портах. Остановка тестовой копии: `docker compose -p webdb-check down`. Тома при этом сохраняются. Не используйте down -v для основного проекта.

## Пример для SQL и EXPLAIN

Из starter выполните:

```bash
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U lab_admin -d webdb < ../examples/schema_demo.sql
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U lab_admin -d webdb < ../examples/seed_demo.sql
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U lab_admin -d webdb < ../examples/queries_demo.sql
```

schema_demo.sql запускается один раз в новом стенде; повторное создание существующих таблиц должно завершиться ошибкой. seed_demo.sql очищает только четыре демонстрационные таблицы demo и создаёт 200 пользователей, 1000 ресурсов, 50 000 заявок и 150 000 позиций детерминированной формулой. Учебный набор служит измерению чтения; он не является полной моделью движения запасов и не заменяет проверки бизнес-инвариантов индивидуального проекта. Индекс для Q1 приведён как комментарий и до исходного измерения не создаётся.

Не запускайте шаблон запроса с именами demo над своей схемой app без адаптации. Для ЛР 3 минимум один итоговый измеряемый запрос должен относиться к индивидуальному проекту. measurements.csv содержит только шапку; фактические измерения заполняет студент. Успехи и ускорения заранее не заданы.

## Отдельный стенд репликации

В ha выполните `bash tools/init-env.sh`, затем `docker compose up -d`. Проверьте `docker compose logs db_standby`. Порты — 55433 и 55434. Если подсеть 172.30.80.0/24 занята, до первого запуска измените LAB_SUBNET в ha/.env. До начала занятия загрузите образы.

Первый запуск primary создаёт роль replicator и public.lab_markers. Standby создаётся pg_basebackup в пустом PGDATA и запускается с standby.signal. У обоих узлов отдельные тома. В учебной конфигурации нет replication slot; wal_keep_size=128MB ограничивает доступность истории при отставании, поэтому длительный простой реплики может потребовать новой базовой копии. Эта настройка рассчитана на короткий лабораторный опыт.

Вход на узлы:

```bash
docker compose exec db_primary psql -U lab_admin -d webdb
docker compose exec db_standby psql -U lab_admin -d webdb
```

Запросы observe.sql разделены комментариями по ролям узлов; выполняйте соответствующую часть, не весь файл на одном узле. На standby:

```sql
SELECT pg_wal_replay_pause();
SELECT pg_is_wal_replay_paused();
SELECT pg_wal_replay_resume();
```

Для опыта с маркерами запустите из ha `bash tools/markers.sh`. После появления записей остановите генератор Ctrl+C и сохраните evidence/acknowledged.csv. Скрипт не перезаписывает существующий журнал. Если нужно повторить опыт, сначала переместите журнал в отдельный каталог своего отчёта. В журнал попадают только успешно завершившиеся INSERT RETURNING. Неопределённый исход потерянного ответа в эту простую проверку не включается.

Отказ: `docker compose stop db_primary`. После фиксации t0 проверьте standby и выполните `SELECT pg_promote();`. После повышения роль определяется `SELECT pg_is_in_recovery();`; запись выполняется на адресе бывшей standby, порт 55434. Старый primary оставьте остановленным. В конфигурации обоих узлов restart=no. После переключения не выполняйте обычный up над тем же стендом без восстановления корректной топологии.

Для повторения опыта: сохраните evidence, выполните `docker compose down` (без -v), затем `docker compose -p webdb-ha-next up -d`. Старый проект остановлен, его тома сохранены; новый проект получает новые пустые тома. Не запускайте два HA-проекта с одной подсетью и одинаковыми портами одновременно. Все дальнейшие команды для новой копии выполняйте с тем же `-p webdb-ha-next`; скрипт markers.sh для неё запускайте как `COMPOSE_PROJECT_NAME=webdb-ha-next bash tools/markers.sh`.

Материалы не содержат автоматического failover, маршрутизации записи или промышленной защиты от split-brain. Порядок исключения старого primary и проверка нового писателя входят в лабораторное задание. Два контейнера одного компьютера не защищают от отказа этого компьютера.

## Остановка

Из соответствующего каталога выполните `docker compose down`. Данные сохраняются в именованных томах. Не удаляйте тома до завершения проверки и сохранения нужных результатов. Изменение паролей .env после первоначальной инициализации не меняет роли в сохранённом кластере.
